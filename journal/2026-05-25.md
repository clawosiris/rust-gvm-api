# 2026-05-25 — MCP Moves to the API Layer, Not the Execution Layer

## Architectural Direction

### MCP belongs in `rust-gvm-api`, not `rust-gvm`
- `rust-gvm-api` is the public API surface layer for `REST` and `gRPC`, so MCP should join that same surface tier instead of being planned inside the lower-level execution repo.
- `rust-gvm` remains the GMP execution substrate: client, protocol, connection, and XML-facing behavior should stay there without taking on public MCP-surface ownership.
- This keeps the boundary clean: `rust-gvm-api` owns customer-facing gateway adapters, while `rust-gvm` stays focused on backend execution against `gvmd`.

## Surface Model

### MCP should be a peer surface to REST and gRPC
- MCP should be treated as a first-class public adapter alongside `REST` and `gRPC`, backed by the same canonical operation catalog and shared gateway core.
- Parity remains the rule: if a customer-facing capability is opened on one shipped surface, the matching exposure on the other shipped surfaces must be planned at the same time or documented as an explicit exception.
- The intended stack is `MCP/REST/gRPC -> rust-gvm-api gateway core -> rust-gvm -> GMP/XML -> gvmd`.

## Why This Way

### The implementation should reuse the gateway we already have, not build a second one beside it
- `rust-gvm-api` already owns the public-contract layer and already carries the `gvm-gateway-*` split, so putting MCP here reuses the existing domain model, session model, and backend adapter seams.
- The real service boundary is still GMP and authenticated `gvmd` sessions. Adding MCP inside the API-layer gateway keeps that boundary intact instead of inventing a second pseudo-boundary in front of it.
- A separate MCP sidecar that forwards into REST or gRPC would add another request-mapping hop, another place for error translation drift, and another place where capability parity can silently break.
- The simpler first deployment is therefore "MCP enters the same gateway runtime as REST," not "MCP calls another proxy that then calls the shared core."

### Keep backend selection explicit even if the first topology is simple
- The likely first deployment uses the same gateway/backend instance for REST and MCP.
- That convenience should stay a default, not a hidden architectural constraint.
- Backend instance selection should remain explicit in configuration so future deployments can route MCP-triggered work differently without redesigning the contract.

## Issues To Watch

### Session handling is the first real architectural trap
- Gateway session tokens map to authenticated backend sessions, so cleanup, expiry, and audit cannot live in the adapter layer.
- MCP must not hide session creation so deeply that reviewers can no longer see where credentials are handled or how backend sessions are reclaimed.

### Surface drift is the second trap
- If REST or MCP starts shipping directly against backend behavior outside the canonical operation catalog, parity becomes aspirational instead of enforced.
- The fix is structural: keep all public surfaces bound to the same operation ids and make missing bindings fail in CI.

### Long-running work will expose whether the design is real
- `targets`, `tasks`, and `reports` are the first domains that will prove whether the shared core truly models scan workflows once or whether each adapter is quietly doing its own thing.
- This is where report size, polling vs. chunking, and connection pinning will stop being theoretical concerns.
