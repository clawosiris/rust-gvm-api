# 2026-05-25 — MCP Moves to the API Layer, Not the Execution Layer

## Architectural Direction

### MCP belongs in `rust-gvm-api`, not `rust-gvm`
- `rust-gvm-api` is the public API surface layer for `REST` and `gRPC`, so MCP should join that same surface tier instead of being planned inside the lower-level execution repo.
- `rust-gvm` remains the GMP execution substrate: client, protocol, connection, and XML-facing behavior should stay there without taking on public MCP-surface ownership.
- This keeps the boundary clean: `rust-gvm-api` owns customer-facing gateway adapters, while `rust-gvm` stays focused on backend execution against `gvmd`.

## Surface Model

### MCP should be a peer surface to REST and gRPC
- MCP should be treated as a first-class public adapter alongside `REST` and `gRPC`, backed by the same canonical operation catalog and shared gateway core.
- Parity remains the rule: if a customer-facing capability is opened on one shipped surface, the matching exposure on the other shipped surfaces must be planned at the same time or documented as an explicit exception.
- The intended stack is `MCP/REST/gRPC -> rust-gvm-api gateway core -> rust-gvm -> GMP/XML -> gvmd`.

## Notes

- This entry records the repo-boundary correction so follow-on MCP planning and implementation land in `rust-gvm-api` rather than drifting into `rust-gvm`.
